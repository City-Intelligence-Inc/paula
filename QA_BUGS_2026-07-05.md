## P0 — blocks core operations / launch risk

### 1. No functioning provisioning path for a non-master Admin or Staff account
**Repro:**
1. As a master admin, go to `/admin/admins` → add a new admin (e.g. `throwawayyysmith+staff@gmail.com`).
2. No invite email arrives at that address.
3. Sign out, try to sign in as that email at `/sign-in` → **"Couldn't find your account."**
4. Clicking "Continue" again does nothing.
5. Separately: navigating directly to an admin-only URL (`/admin/students`) while signed in under a freshly-created identity for that email redirects to `/dashboard` — the **parent/family Client Portal**, gated behind "save a card to unlock your family portal."

**Impact:** only the existing bootstrap master admins can do anything in the system. A real new hire added the intended way (Admins page) cannot get a working login at all. This is the same root cause as the already-tracked backlog item ("team accounts land in the parent portal by default instead of a portal picker" — spun off separately, chip `task_bf073fdb`), but confirmed here to be more severe than originally scoped: it's not just a wrong landing page, it's a **dead end** with no admin access ever reachable.

**Suspected cause:** adding a row to the admins table doesn't provision a matching Clerk identity/invite; any fresh sign-up under that email instead falls through to the default "family" role path.

### 2. "Session Notes" feature is fully built and wired to live data, but unreachable from anywhere in the site
**Where:** `website/src/app/staff-log-session/page.tsx` (640 lines; comment explicitly says `// /staff-log-session — Session Notes (FEATURE_LIST Roles + Notes)`, has a working LIVE mode wired to `/api/students/:id/session-notes`).

**Repro:** grep the whole app for `staff-log-session` — zero references outside its own page file. No nav item, no button, no link anywhere points to it.

**Impact:** this looks like the intended full implementation of the "Session Notes" item from the features list (role switcher for Super Admin / Office Staff / Tutor / Parent / Student, Session Plan / Activities / Private Notes / Public Notes columns) — built and functional, but completely invisible to real users. What's actually live and discoverable is a much simpler, separate "Log a session" billing form (`/admin/sessions/new`) plus a basic free-form notes block on each student's admin page.

**Ask Ari:** ship `/staff-log-session` with a real nav entry (and decide who should see it — the role switcher suggests it), or confirm it's superseded by the simpler in-page notes and should be removed as dead code.

### 3. Student creation fails with a raw database error when the Parent Name field has no space
**Repro:**
1. `/admin/students` → New Student.
2. Enter a single-word Parent Name (e.g. `asd`), fill the rest, Save Student.
3. Fails with: `Failed: {"error":"Create failed","detail":"ValidationException: One or more parameter values are not valid. A value specified for a secondary index key is not supported. The AttributeValue for a key attribute cannot contain an empty string value. IndexName: by-family, IndexKey: lastName"}`
4. Works if Parent Name has two words (e.g. `Asd Parent`).

**Impact:** two bugs bundled together:
- **(a) Functional:** a single-word parent name blocks student creation outright — almost certainly because the code splits "Parent Name" into first/last on whitespace, and an empty derived `lastName` can't be written to a GSI sort key.
- **(b) Info disclosure / UX:** the raw AWS/DynamoDB exception text is shown directly to the admin instead of a friendly validation message. Admins shouldn't see internal table/index names.

## P1

### 4. File uploads return a bare 403 for every file type, even as Master Admin
**Repro:** any student page → Shared files → drag a PDF or video → fails, `403`, for both file types, signed in as the highest-permission account.

**Impact:** blocks file-sharing entirely, and blocks QA of tests 3.3 (file privacy), 5.1 (upload), 5.2 (viewing) outright — there is currently no way to create a file to test privacy scoping against.

**Note:** the QA guide's own setup section anticipated this ("if storage isn't switched on, you should see a tidy 'uploads not set up' message rather than an error") — so at minimum the error handling needs to distinguish "storage not configured" from "actually forbidden." Worth checking whether S3/storage env vars are even set on this deployment.

## Addendum — cross-checked against Ari's `640a02d` / `fea1988`, pushed mid-session

While writing up this doc, `git pull` picked up two new commits from Ari pushed today (`640a02d "fix(C-1/B-5): registration card gate actually fires"`, `fea1988` theme-key fixup for the resulting build break). Two direct connections worth flagging before this doc gets acted on:

1. **This commit is very likely the direct cause of Bug #1/#5** (new admin/staff accounts landing in the parent Client Portal, card-gated). The commit message says plainly: *"New accounts land on /onboarding (SignUp `forceRedirectUrl`)"* — this now applies to **every** new sign-up, with no branching by intended role. `GET /api/onboarding` only ever looks in the `parents` table; a staff/admin/tutor invite has no parent row, gets `{parentId: null, needsInfo: true}` back, and the onboarding page has no fallback for "this isn't a parent at all" — so it just renders the parent 3-step flow (info → card → done) for everyone. **Suggested fix:** have `/api/onboarding` (or the page itself) check the user's actual role/invite type first, and only run the parent card-gate flow for actual parent sign-ups.
2. **Ari's commit message claims file uploads are fully operational** ("`FILES_S3_BUCKET` is set in production — F-1 presign returns 200, drag-drop uploads fully operational") — this **directly contradicts** Bug #4 above, where we saw a bare 403 on every upload attempt, even as master admin. Possible explanations, worth checking in this order: (a) our test ran against a build from *before* whatever fixed this, and it's already resolved — re-test after confirming `fea1988` is deployed; (b) the *presign* step (getting a signed upload URL) succeeds, but the actual `PUT` to S3 fails separately — e.g. a bucket CORS or policy issue, not a missing env var. If it's (b), it wouldn't show up in a presign-only check, so it's worth re-testing the full drag-and-drop path end-to-end, not just the presign call.

Recommend re-running tests 1.1 (staff/admin provisioning), 5.1/5.2 (uploads), and 3.3 (file privacy) once `fea1988` is confirmed deployed — some or all of the P0/P1 findings above may already be stale.
